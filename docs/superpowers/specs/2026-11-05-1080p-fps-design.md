# 1080p downscale and FPS cap — design

Date: 2026-11-05

## Goal

1. Add a real **1080p** resolution option that downscales 1440p/4K sources to
   1080p. **orig** (no scaling) stays.
2. Add an **FPS** setting: **30 / 60 / orig**.

Both settings are available on every surface: desktop GUI, CLI, presets, Web UI,
OBS dock, and remote mode.

## Constraint: `"1080p"` already means "orig"

Today the token `"1080p"` means *no scaling*:

- `presets.RESOLUTIONS = ("1080p", "720p", "480p")`; a preset saved with "orig"
  in Advanced mode is stored as `"resolution": "1080p"` in `settings.json`.
- `gui/layout.py`: `DEFAULT_RESOLUTION = "1080p"`, rendered with the label "orig".
- `dock_server.build_args`: `"1080p"` → `--no-small`; `dock.html` has a `1080p`
  radio with the same meaning.
- `server._preset_resolution_to_radio`: `"1080p"` → `"No change"`.

If `"1080p"` simply takes on its new meaning, existing user presets silently
start downscaling 4K/1440p sources. The design therefore introduces a new
canonical no-scale token and migrates stored presets once.

## 1. Resolution

### Canonical values

`"orig"`, `"1080p"`, `"720p"`, `"480p"`. `presets.RESOLUTIONS` becomes
`("orig", "1080p", "720p", "480p")`.

### Migration

`settings.json` gets a top-level marker `presets_version`. When presets are
loaded and the marker is absent or `< 2`, every stored preset with
`"resolution": "1080p"` is rewritten to `"orig"`, every stored preset that has a
`resolution` but no `fps` gains `fps: "orig"` (v1 presets implicitly kept the source
frame rate; resolution-less presets such as mp3 are untouched), `presets_version: 2` is
written, and the file is saved. The marker is what makes the migration
one-shot: without it, an old `"1080p"` (= orig) cannot be told apart from a new
`"1080p"` (= downscale) on a later load. A fresh install seeds
`DEFAULT_PRESETS` and writes `presets_version: 2` at the same time. A failed
write leaves the in-memory presets migrated, and the migration runs again on the
next load.

### Approach A: height-based edges

The pipeline is already height-based (`ProcessingOptions.small` +
`small_target_height`). Only the edges use the `small`/`small_480` booleans. The
edges move to a height too.

- **CLI**: a new `--1080` flag next to `--480`/`--720`. All three write one
  destination, `small_height` (`store_const` 480/720/1080), and keep working
  only together with `--small`, as today. `--480`/`--720` keep their current
  meaning. `_apply_preset_to_args` maps the preset resolution to
  `small` + `small_height` (`orig` → `--no-small`) and honours explicit flags by
  checking `small_height` instead of `small_480`. The `--480 without --small`
  warning becomes "`--480`/`--720`/`--1080` has no effect unless `--small` is
  also provided". `cli.py` sets `option_kwargs["small_target_height"]` from
  `small_height`.
- **GUI**: `small_480_var` is replaced by `small_height_var` (IntVar,
  480/720/1080, default 720). `small_var` stays. `resolution_from_small` and
  `apply_resolution_choice` map between `orig/1080p/720p/480p` and
  `(small_var, small_height_var)`. `DEFAULT_RESOLUTION` becomes `"orig"`. The
  `SegmentedChoice` shows **1080p / 720p / 480p / orig**. `GUIPreferences` gets
  a new `small_height` key; on read, a missing `small_height` falls back to the
  legacy `small_video_480` (`True` → 480, else 720). `_collect_arguments`, the
  seeded-launch CLI flags, and `apply_preset_to_gui` use `small_height_var`.
- **Create-link dialog** (`gui/shortcut.py`): gains a **1080p** checkbox next to
  720p/480p. The three sizes are mutually exclusive and imply Small. It emits
  `--small --1080`.
- **Remote** (`service_client.send_video`): see §4. The CLI remote path also
  stops passing `small_480` twice: it went both in `remote_option_values` and
  as an explicit keyword, which raised a `TypeError` for `--url --small --480`
  and silently fell back to local processing.
- **Web UI**: the Resolution radio becomes `["No change", "1080p", "720p",
  "480p"]`. `_resolution_to_flags` returns `(small, target_height)`.
  `_preset_resolution_to_radio` maps `"orig"` → `"No change"` and `"1080p"` →
  `"1080p"`.
- **Dock**: `dock.html` gets radios **1080p / 720p / 480p / orig**, with
  `orig` → `--no-small`, `1080p` → `--small --1080` and `720p` → `--small --720` in
  `dock_server.build_args`. `ALLOWED_RESOLUTIONS` gains `"orig"`. The dock does
  not persist resolution in `localStorage`, so nothing there needs migrating. A
  dock page cached from an older version that sends `"1080p"` would now
  downscale; this is accepted.

### Pipeline

- `_scale_filter_part` scales only when `original_height > target_height`
  (today: `>=`). A 1080p source with a 1080p target logs "Keeping original
  resolution" and adds no `scale`, so CUDA decoding is not disabled for a no-op.
  This also stops the useless rescale for 720p sources at 720p.
- Output filename: `_input_to_output_filename` adds a `1080` token for a
  1080p target (`_small_1080`), alongside the existing `480`.

## 2. FPS cap

### Semantics

The setting is a cap, never an increase: output fps = `min(source_fps,
max_frame_rate)`. A 30 fps source with "60" stays 30, the same way resolution
never upscales. The pipeline logs when the cap applies
(`Capping frame rate from 59.94 to 30 fps`).

### Options

`ProcessingOptions.max_frame_rate: Optional[float] = None` (`None` = orig). The
name is distinct from the existing `ProcessingOptions.frame_rate`, which is the
probe fallback.

### Filter placement

The `setpts` expression from `chunks.get_tree_expression` is indexed by `N` over
**source** frames and divides by `FR`. Lowering fps before `setpts` would
renumber `N` and shift chunk boundaries. Therefore:

- Speed path (`pipeline.py`, filter graph with `setpts`): keep the current
  `fps={source}` before `setpts`, and append `fps={output_fps}` **after**
  `setpts` when the cap applies.
- Scale-only path (`_build_scale_only_filter_graph`): the existing
  `fps={frame_rate}` uses `output_fps` instead.

### Consumers of frame rate

- Uses **output** fps: GOP/keyframe sizing (`frame_rate=` passed to the final
  command builder), the final-encode frame count for progress
  (`final_total_frames`, scaled by output/source) and the final-duration logs,
  and the frame rate reported in the result.
- Stays on **source** fps: `samples_per_frame`, chunk construction, and the
  audio-extraction estimate (`estimated_total_frames`, which reads the input).

No filename token for fps.

## 3. Surfaces

- **CLI**: `--fps {30,60,orig}` (also accepts any positive number) →
  `max_frame_rate`; `orig` → `None`. Default: orig.
- **GUI (Advanced)**: an **FPS** row (`SegmentedChoice` **30 / 60 / orig**)
  directly under the Resolution + Codec pair. It follows the Codec row pattern:
  a plain `SegmentedChoice` bound to a `StringVar`, with a trace into
  `refresh_advanced_preset_selection`. `layout.add_segmented` is for the
  `DoubleVar` speed knobs only. `apply_preset_to_gui` writes `fps_var` directly.
  Backed by `fps_var` (StringVar `"30"`/`"60"`/`"orig"`), persisted as
  `GUIPreferences` `fps`, sent by `_collect_arguments` locally and remotely.
  Simple mode hides `basic_options_frame`, so there fps comes from the selected
  preset only. Row spacing uses `SETTING_ROW_PADY`.
- **Presets**: a new sparse field `fps: Optional[str]` with values `"30"`,
  `"60"`, `"orig"`. If the field is absent, fps is left alone; `"orig"` forces
  no cap. The field is added to `PRESET_VALUE_FIELDS`, `PRESET_FIELD_LABELS`
  (`"FPS"`), `preset_dialog.FIELD_SPECS` (derived), `describe_preset`,
  `match_preset` (exact compare), `layout.build_sparse_preset`,
  `apply_preset_to_gui`, `cli._apply_preset_to_args` and
  `presets.preset_to_cli_args`, and `server.preset_to_web_controls`.
- **Web UI**: an FPS radio `["orig", "60", "30"]` (default orig), passed to
  `_stream_pipeline` and set by presets.
- **Dock**: an FPS select in the ⚙️ settings panel. It stays there
  permanently, like Codec, and is not relocated by the preset/Custom logic.
  `dock_server.build_args` maps it to `--fps`, and `build_args` validates it
  (`"orig"`, `"30"`, `"60"`). With a preset selected, the preset's own fps
  applies via `--preset` and the FPS control is ignored.

## 4. Remote API compatibility

`/process_video` in `server.py` gets two optional trailing parameters:
`target_height: int = 0` (0 = use the `small_480` flag as today) and
`max_frame_rate: float = 0` (0 = orig). `send_video` gains
`small_height: Optional[int]` and `max_frame_rate: Optional[float]`, and
appends the two positional args **only when at least one is non-default**
(1080p target or an fps cap). A new client therefore keeps working with an old
server for every option that existed before. For 480p it still sends
`small_480=True`. Only the new options need an updated server. The server-side
mapping prefers `target_height` when non-zero.

## 5. Default presets (fresh installs only)

- **Compress**: resolution `720p` → `1080p`, plus `fps="30"` (h.264, silence ×1
  unchanged).
- **Smallest**: plus `fps="30"`.
- **Compatible** and **Optimal**: plus `fps="orig"`, so selecting them after a capped
  preset resets the cap instead of inheriting it. **mp3** stays without resolution and fps.

Existing installs keep the presets already stored in `settings.json`. The only
change they see is the `1080p` → `orig` migration.

## 6. Testing

- Preset migration: a `1080p` preset becomes `orig`, the marker is written, and
  a second load with a real `1080p` preset leaves it alone. A fresh seed writes
  the marker.
- CLI: `--1080`/`--480`/`--720` → `small_target_height`; `--fps 30/orig`;
  preset precedence with explicit flags; the legacy warning text.
- Pipeline: the filter graph has `fps=30` after `setpts` when capping 60 → 30;
  no extra `fps` when source ≤ cap; the scale-only graph uses output fps; GOP
  uses output fps; a 1080p source at a 1080p target adds no `scale`.
- Filename: a `_small_1080` token.
- Presets: `fps` round-trips sparse, `describe_preset` lists it,
  `match_preset` compares it.
- GUI: resolution/fps projection; `fps_var` follows the Codec pattern (a StringVar, not in `_slider_updaters`); extend
  `test_basic_options_frame_grid_positions_do_not_collide` for the FPS row;
  `GUIPreferences` legacy `small_video_480` fallback.
- Remote: `send_video` sends 13 positional args for defaults/480p/720p and 15
  when the target is 1080p or fps is capped. The server maps `target_height`.
- Dock: `build_args` for `orig`, `1080p`, and `--fps`.

Update `README.md`, `docs/cli.md`, `docs/gui.md`, `docs/obs-dock.md` and the

## Out of scope

- Upsampling fps or resolution.
- Arbitrary fps values in the GUI or Web UI (the CLI accepts them).
- Migrating existing users' Compress/Smallest presets to the new defaults.
